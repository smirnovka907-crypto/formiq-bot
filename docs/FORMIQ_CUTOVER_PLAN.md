# FORMIQ — план переезда Render → Timeweb, подготовка БЕЗ запуска

**Статус:** только проектирование, Draft PR #36. Нет купленного VPS/Managed PostgreSQL, SSH, серверных секретов или разрешения на публикацию. Без отдельного разрешения нельзя делать merge, deploy, оплачивать или перенастраивать Telegram/Render. Успешный локальный `current` symlink не является откатом новых записей в PostgreSQL.

## Этап 1 — подготовка без изменения production

1. Получить настоящую зашифрованную копию Render через `docs/FORMIQ_WINDOWS_BACKUP_RUNBOOK.md`; выполнить restore в локальную пустую PostgreSQL 18 и сверку. Без этого **NO-GO**.
2. Сверить фактические схемы, расширения, функции, sequences, статусы workout и историю, список миграций с `main` и открытых PR; зафиксировать SHA и набор проверок. Действующий Render оставить без изменений.
3. Подтвердить юридическую допустимость Timeweb *конкретного сегмента* под анкеты и чувствительные сведения, договор, регион РФ, модель расходов, offsite encryption/retention и доступ физических лиц. До письменного подтверждения **NO-GO**.
4. Для будущих обновлений определить владелец-утверждаемый одноразовый релиз: GitHub Environment `timeweb-production` с required reviewers; секреты окружения только в защищённых настройках; workflow_dispatch от точного SHA; `concurrency` serializes deploys; `pull_request_target` не использовать. В Issue #35 workflow `future-deployment-disabled` остаётся `if: false` без SSH и deploy.
5. До отдельного одобрения не создавать VPS, managed DB, хранилища или DNS.

## Этап 2 — первичная настройка ПОСЛЕ отдельного разрешения владельца

1. Оплатить только утверждённые Timeweb VPS (Россия), приватную Managed PostgreSQL **18**, защищённую по требованиям ПДн конфигурацию и offsite backup. База не имеет публичного IPv4.
2. Настроить системные обновления, firewall: **443**, 80 только для ACME, SSH только с выделенных адресов; запретить root SSH; отдельные системные роли `formiq` (web) и минимальную `formiq-deploy` с узкими правами. Разрешение только на строго определённый restart `formiq-web.service`, не произвольный sudo.
3. Создать VPS directory `/srv/formiq/releases/<full-sha>` и атомарный `current`; service secrets хранить только в `/etc/formiq/web.env` с правами системного пользователя и вне GitHub. Шифровальный ключ для offsite backup хранить отдельно.
4. Установить nginx TLS/Let's Encrypt, gunicorn bind **127.0.0.1:8080** из `deploy/timeweb/formiq-web.service`. Пути `/__timeweb_release_health` и `/__timeweb_db_health` открыть **только из loopback**. Сервер WSGI лишь обрабатывает HTTP, не делает init_db/replay_pending/set_webhook.
5. Проверить отдельно WSGI role и запрет привязки к Render PostgreSQL; проверить точный SHA, `SELECT 1`, PG18 и обязательные таблицы через loopback readiness. Тестовые dummy-токены — только для синтетического контура, **не включать настоящий @formiqcoachbot**.

## Этап 3 — bootstrap и миграции, отдельно от веб-запуска

1. Восстановить только зашифрованную копию в **новую изолированную пустую** PostgreSQL 18 в приватной сети, затем сверить counts/FK/PK/sequences/все существующие пользовательские состояния. Не применять схему к production во время обычного systemd restart.
2. Зафиксировать список миграций и SHA приложения, проверить их на другом disposable PG18: применить один раз и повторно (идемпотентность), валидировать обратную совместимость старых данных/истории, объёмы блокировок и lock_timeout. Миграция необратимого типа = отдельный GO/NO-GO, **откат бинарника её не исправляет**.
3. Только при отдельном разрешении и проверенных backup/restore выполнять *однократный* `init_db()` и разрешённые миграции как **отдельный операторский этап**, импортируя модуль без запуска его `if __name__ == '__main__'`. Не запускать `python main.py` на будущей VPS: существующий `run_legacy_render()` запускает Telegram setters и webhook. После каждого migration повторить сверку; сохранить baseline checksum/counters.
4. Telegram `replay_pending()` — **не bootstrap БД и не автоматический веб-старт**. Её разрешено запускать только после единоличного cutover и fencing старого обработчика, при гарантированном единственном потребителе `incoming_updates`; повторная обработка защищена idempotency, но не проверена под параллельными активными процессами.

## Этап 4 — cutover с сохранением новых записей, отдельное разрешение

1. Назначить окно обслуживания и согласовать RPO=0 как **цель**, а не обещание без испытания. Заранее протестировать restore и Telegram на синтетическом контуре; сохранить план остановки записи.
2. Перевести существующий Render в согласованный **режим только чтения / временной остановки обработки записей**. Проверить фактически, что новые HTTP записи и Telegram updates не принимаются двумя средами. Нельзя объявлять freeze только по флагу без read-only теста. При необходимости безопасно остановить старый процесс через провайдера после отдельного разрешения.
3. Зафиксировать checkpoint полученных и ожидающих Telegram update IDs; не подтверждать Telegram webhook обновление, если оно ещё не сохранено надёжно. Учесть сообщения, пришедшие во время freeze, и не дублировать/не терять их.
4. Снять **новый финальный** pg_dump от ещё доступного Render, зашифровать, проверить SHA/GCM/TOC, восстановить его **в чистую приватную Timeweb PG18**, сверить таблицы, запись истории, согласия, даты/таймзоны, FK, PK, sequences и входящие updates. Если расходится хоть одно контрольное значение — оставить Render единственным активным.
5. После отдельного явного разрешения переключения одновременно согласовать внешний HTTPS URL Mini App и **ровно один** `@formiqcoachbot` webhook, `set_webhook` с защищённым secret_token. Изменять branding только при утверждённых правилах, не запускать `run_legacy_render` на VPS. Проверить URL SSL, Telegram initData, API, личный профиль/питание/тренировки и DB health.
6. Только после доказательства, что старый Render **не записывает**, разрешить новый единственный web worker и отдельный `replay_pending` по checkpoint. Нельзя позволять обоим серверам одновременно принимать updates или записывать в разные базы.
7. В течение контрольного периода проверять новые пользовательские записи и сравнивать счётчики; Render/старую БД не удалять, но **не запускать параллельно**.

## Этап 5 — два разных типа отката

1. **Ошибка кода без смены схемы и без переезда БД:** атомарно переключить `current` на старый проверенный SHA, перезапустить ровно `formiq-web.service`; healthcheck требует **и SHA, и PG18/обязательные таблицы**. Все новые записи остаются в **той же** PostgreSQL, не откатывать её на старый snapshot. Версии должны быть совместимы со схемой.
2. **Ошибка после смены провайдера/базы:** нельзя просто вернуть webhook на старый Render, поскольку новая БД уже содержит свежие записи. Сначала поставить **единственный новый writer на паузу**, зашифровать текущую новую БД, сверить с последним checkpoint, экспортировать/reconcile все новые записи и ожидающие updates, восстановить согласованное состояние на целевой стороне, проверить PK/sequences/idempotency/временные зоны, и только затем **с отдельным разрешением** переключить webhook/адрес. Если согласованное перенесение новых записей не доказано — оставить систему в режиме обслуживания, а не допускать потерю истории.
3. **Миграция схемы несовместима:** никакого автоматического rollback по symlink. Безопасный путь — отдельный исправляющий релиз/forward-fix, либо восстановление по одобренному плану после полного дампа изменившейся БД. Запрещены DROP/DELETE и автоматическое восстановление backup поверх существующих записей.
4. Наблюдаемость: статусы GitHub PR/CI exact HEAD, TLS, HTTP p95/5xx, WSGI health, PG health, наличие последних encrypted offsite backups, проверенные restore-drills, отсутствие secrets/medical info в логах. Конечная эксплуатационная готовность — только после реального теста на оплаченной и разрешённой инфраструктуре.

**Главный блокер на 27.10.2026:** Render Free PostgreSQL истекает **19.11.2026, 22:50 МСК**, реальная encrypted production копия + успешный отдельный restore пока НЕ подтверждены. Эта документация не является утверждением о запуске или соответствии 152-ФЗ.
