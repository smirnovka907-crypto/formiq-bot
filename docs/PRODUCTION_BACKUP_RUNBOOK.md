# FORMIQ — production PostgreSQL 18: private backup / restore playbook

**Дата проверки:** 2026-10-24. **Статус: production backup НЕ создан, restore НЕ проведён. NO-GO.**

Разрешение владельца: только безопасное чтение production для резервной копии,
восстановление ВНЕ production и подготовка PR №15. **Не разрешены**
деплой, production-миграции, merge в main, изменение токена/webhook,
новые боты/платные ресурсы или удаление пользовательских данных.

## Почему ChatGPT не может прямо сейчас снять production dump

- GitHub app умеет изменять файлы и проверять GitHub Actions, но не выдаёт
  секреты репозитория, не выполняет private shell и не даёт private backup storage.
- Render connection предоставляет read-only SQL, статусы, логи и deployment
  metadata, но **не** `pg_dump`, SSH/shell и файловый encrypted export.
- На Render **Free PostgreSQL нет managed backups / PITR**; Render Free web
  не предоставляет Shell/SSH/one-off jobs, а его файловая система эфемерная.
- GitHub Actions имеет тестовую disposable PostgreSQL 18, но доступных
  проверенных secret-подключений к production или защищённому хранилищу
  резервной копии **нет**. Нельзя складывать SQL/данные пользователей в
  публичный репозиторий, workflow-artifacts, логи или чат.

**Один необходимый доступ:** доверенный личный компьютер владельца с PostgreSQL
client 18 и Python 3.12+, из которого владелец сам введёт *External Database URL*
из Render Dashboard непосредственно в скрытый локальный prompt. URL никогда не
копируется в чат или GitHub. Код и безопасные проверки подготовлены в PR №15;
действия выполняются локально, без дополнительного сервера или подписки.

## Как снять защищённый архив на доверенном компьютере

1. На личном ПК получить текущую ветку PR №15 из GitHub. Не запускать
   из публичного GitHub Actions runner, Render Free web или общего компьютера.
2. Установить **PostgreSQL 18 client utilities** (`pg_dump`, `pg_restore`,
   `psql`), Python 3.12+ и только локальную зависимость:
   `python -m pip install -r requirements-backup.txt`.
3. Открыть Render Dashboard → Kirill's workspace → **formiq-db → Connect**.
   Взять именно *External Database URL*, не Internal URL. Он будет запрошен
   скрытым вводом (пароль и адрес не печатаются, не попадают в аргументы процесса).
4. На доверенном ПК запустить:
   `python scripts/formiq_pg_backup.py backup`.
   Ввести External URL в скрытый prompt; придумать **уникальную длинную
   парольную фразу (не менее 20 символов)** и надёжно сохранить её отдельно
   в личном менеджере паролей. Она нужна и для проверки, и для восстановления.
5. Скрипт запускает `pg_dump` версии 18 с custom archive и
   `default_transaction_read_only=on`, шифрует поток **AES-256-GCM**
   со случайными солью/nonce и scrypt KDF до записи в файл
   `~/FORMIQ-private-backups/*.fiqenc`. Запрещена запись внутри checkout
   репозитория. Скрипт завершается ошибкой, если `pg_dump` неуспешен.
   По завершении проверяет расшифровку, GCM authentication tag и
   `pg_restore --list`; выводит только путь и SHA256 *зашифрованного* файла.
6. Запустить повторную проверку (ввод фразы скрытый):
   `python scripts/formiq_pg_backup.py verify <PATH_TO_FIQENC>`.
   Сверить SHA256, не публикуя пароль и файл.
7. **Сам локальный файл — только первая защищённая копия, не off-site
   backup.** Перенести **только зашифрованный** `.fiqenc` в приватное
   долговременное хранилище с MFA (например, личный Drive/OneDrive с закрытым
   доступом). Сохранить второй экземпляр вне ПК. Ключ/парольная фраза
   хранится отдельно, не в том же каталоге/сообщении. Проверить наличие
   загруженного объекта и его SHA256 после повторного скачивания. Не
   отправлять ссылку с публичным доступом.

## Изолированное восстановление — только после создания реального архива

- На **доверенном локальном компьютере** создать отдельную ПУСТУЮ PostgreSQL
  18 базу `formiq_restore`. Её сервер должен слушать **только localhost**.
  Не подключать Telegram bot, webhook, Yandex и производственные токены.
- Выполнить `python scripts/formiq_pg_backup.py restore <PATH_TO_FIQENC>`.
  Инструмент **сначала** аутентифицирует архив и проверяет `pg_restore --list`,
  затем скрыто спрашивает URL локальной `*_restore` базы и проверяет её
  пустоту/версию 18. Любой remote URL или имя `formiq_db` запрещены.
  Восстановление выполняется `pg_restore --single-transaction --exit-on-error`,
  **без --clean, DROP и --create**. Если возникла ошибка, production не
  затрагивается. Локальная восстановленная база содержит персональные данные:
  не копировать её в общие каталоги, CI, логи или чат.
- После восстановления проверить counts / PK / foreign keys и данные
  `profiles`, `profile_metrics`, `health_limits`, `training_cycles`,
  `scheduled_sessions`, `workouts`, `workout_items`, `workout_sets`,
  `cardio_sessions`, `pending_inputs`, `rest_timers`. Отчёт содержит
  **только агрегированные счётчики** и результаты целостности, не строки.
  Проверить, что завершённые и активные подходы, веса, кардио и календарь
  целы. Записать время восстановления, SHA256 и ошибки.
- Применить точную `migrations/20261023_weekday_schedule.sql` на **этой
  копии**, затем повторно: дважды для идемпотентности и после — тесты
  `auto/manual/retired`, новый график и совместимый emergency
  `FORMIQ_SCHEDULE_SAFE_MODE=1`. Продакшен не менять.
- Положительный `verify` или тест synthetic CI **не заменяет**
  успешного real-data restore.

## Срок действия и постоянная защита

- `formiq-db` — Free Render PostgreSQL 18; точное `expiresAt`:
  **2026-11-19T19:50:15Z**. В день истечения Free БД станет недоступной;
  дальнейшие **14 дней** — лишь grace-period для upgrade, не для
  полноценной эксплуатации. После него Render удалит базу.
- До 19 ноября сделать **первый действительный encrypted backup и
  изолированный restore**, затем выбрать с владельцем устойчивый вариант
  (например, обновление существующей Render PostgreSQL на платный план с
  managed backup/PITR; стоимость согласовать отдельно). Одними
  локальными dump без поддерживаемой БД нельзя обеспечить работу бота
  после окончания Free тарифа. Новый бесплатный экземпляр раз в 30 дней
  не является безопасной постоянной стратегией.
- До перехода на устойчивый план — **ежедневный** зашифрованный снимок,
  дополнительный непосредственно перед любой миграцией и выпуском.
  Минимально: 7 дневных и 4 недельных резервных копии в приватном
  off-device хранилище; раз в месяц и непосредственно перед релизом
  проводить **реальный test restore** на изолированной PG18.
  Ротацию делать только после проверки последней восстановимой копии.
- Backup passphrase хранить отдельно в менеджере паролей, с доступом только
  владельцу. Не оставлять копии в temporary folders GitHub/Render.
